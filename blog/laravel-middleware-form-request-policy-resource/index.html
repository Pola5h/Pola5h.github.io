Laravel Middleware vs FormRequest vs Policy vs Resource: Layered API Security in Laravel 13

One of the most common architectural mistakes in Laravel APIs is stuffing auth checks, validation, ownership rules, and JSON formatting into controllers. Here is the exact 5-layer request lifecycle I use in production Laravel 13 apps — from bootstrap/app.php to 404-first Policies and match (true) exception handling.

TL;DR — The One-Line Mental Model

Middleware checks who you are at the door. FormRequest checks what you brought. Policy checks whether this exact record belongs to you. Service executes the transaction safely. Resource shapes what leaves the server.

1. Middleware vs FormRequest vs Policy vs Resource (At a Glance)

Every senior Laravel code review and backend interview eventually hits the same question: "Why split checks across Middleware, FormRequest, Policy, and Resource when you could write them all in the controller?"

The answer is Defense in Depth and Separation of Concerns. Think of an API request like boarding a flight at an airport:

  1. Main Gate Security (Middleware): "Who are you? Do you have a valid passport and visa?" — Validates your JWT token, email verification status, and forces JSON headers before your payload ever touches the controller.
  2. Luggage Scanner (FormRequest): "What is inside your bag? Is the weight and file type allowed?" — Sanitizes fields, enforces MIME types and upload size limits, and rejects bad input with 422 before touching the database.
  3. Seat Boarding Check (Policy): "Everything checks out, but is seat 12B actually yours?" — Verifies object-level ownership ($document->user_id === $user->id) so users can never view, edit, or delete someone else's data.
  4. Packaging & Customs Exit (Resource): "What is allowed to leave the terminal?" — Whitelists safe fields and strips internal database columns, foreign keys, and encrypted secrets.
Layer Directory Primary Question Failure Status

FormRequest app/Http/Requests Is the incoming payload valid, sanitized, and permitted? 422 / 403

2. The Full Laravel 13 Request Lifecycle

When a client sends a request like PUT /api/documents/42 in a modern Laravel 13 SaaS API, it travels through a strict one-way dependency chain: Route → Middleware → FormRequest → Controller → Policy → Service → Model → Resource.

Notice the golden rule: Controllers never run Eloquent queries, touch files, or call third-party APIs. Services never read request() or return HTTP responses — they throw domain exceptions that bootstrap/app.php translates into clean JSON. (If you want a deeper dive into thin controllers, see my MVCS Architecture in Laravel guide.)

3. Layer 1 — Middleware in bootstrap/app.php (No Kernel.php)

Prepending ForceJsonResponse runs before the controller so that a missing Accept: application/json header never causes Laravel to redirect an unauthenticated API request to an HTML /login page:

Appending SecurityHeaders runs after the response is built, protecting every web and API endpoint against three classic browser attacks:

  • X-Frame-Options: DENY — Blocks clickjacking by forbidding attackers from embedding your app inside an invisible <iframe>.
  • X-Content-Type-Options: nosniff — Stops browsers from MIME-sniffing uploaded images or text files as executable JavaScript (preventing stored XSS via disguised uploads).
  • Referrer-Policy: strict-origin-when-cross-origin — Strips paths and query strings (like /verify-email?token=secret...) when a user clicks an external link, sending only the bare origin so tokens never leak into third-party server logs.

4. Layer 2 — FormRequest (Input Guard & RBAC Field Protection)

A FormRequest runs before your controller method executes and handles three distinct jobs in order: prepareForValidation() (sanitization), authorize() (request permission), and rules() (field validation).

Why Document::class Instead of a $document Object?

During a POST request, no Document row exists in the database yet. Calling $this->user()->can('create', Document::class) asks Laravel's central Gate to look up the policy registered for Document::class in AppServiceProvider and call DocumentPolicy::create(User $user).

Always Use $request->validated(), Never $request->all()

Passing $request->all() to a model or service is how mass-assignment vulnerabilities happen. If an attacker injects is_admin: true or user_id: 1 into a JSON body, $request->validated() strips every key that wasn't explicitly declared in rules().

Handling Admin-Only Fields cleanly

When regular users and admins edit the same model, you have two clean patterns:

  • Conditional prohibited rules: Allow is_featured or status when $this->user()?->hasRole('admin'), and set them to ['prohibited'] for regular users so tampering triggers an explicit 422.
  • Dedicated Admin Endpoints (Enterprise approach): Split into /api/v1/documents/{id} (UpdateDocumentRequest) and /api/v1/admin/documents/{id} (AdminUpdateDocumentRequest behind role:admin middleware). Zero if/else branching inside validation rules.

5. Layer 3 — Policy & Two-Layer Ownership (Why 404 Beats 403)

Suppose User A owns Document #42, and User B sends GET /api/documents/42 or DELETE /api/documents/42. Most tutorials fetch Document::findOrFail(42) and let the Policy throw a 403 Forbidden.

The security problem with 403: Returning 403 Forbidden tells an attacker, "Document #42 definitely exists in this database — it just belongs to someone else." That enables IDOR resource enumeration.

Instead, use two-layer ownership defense:

If User B requests Document #42, Layer 1 throws ModelNotFoundException → 404 Resource not found, leaking zero information. If a future developer accidentally swaps in an unscoped Document::find($id), Layer 2 (DocumentPolicy) still blocks the breach with 403.

6. Layer 4 — Service Layer & DB::transaction() File Safety

Combining file uploads with database writes is a classic source of production corruption. Without careful ordering, you either leak orphan files on disk or leave broken download links in MySQL.

On Delete: Commit the DB Delete Before Deleting the File

If you deleted the file first and the database transaction rolled back, the database record would survive while the file was permanently gone — leaving broken attachments across your UI. Committing the DB delete first eliminates that failure mode.

8. Common Anti-Patterns to Avoid

  1. Returning 403 on unscoped lookups: Always scope by $user->relation()->findOrFail($id) first so attackers cannot enumerate IDs.
  2. Using $request->all() instead of $request->validated(): Opens mass-assignment holes the moment a new column is added to $fillable.
  3. Putting request() or response() inside Services: Makes your service impossible to reuse in Artisan commands, jobs, or unit tests.
  4. Skipping ForceJsonResponse on API routes: One missing Accept header turns a 401 JSON error into a broken HTML redirect.
  5. Deleting files before DB commit: Always delete from disk after DB::transaction() succeeds.
  6. Putting generic exception interfaces above specific ones in match (true): Always list specific exceptions (NotFoundHttpException) before parent interfaces (HttpExceptionInterface).

9. Frequently Asked Questions

What is the difference between Middleware, FormRequest, Policy, and Resource in Laravel?+

Middleware enforces authentication, email verification, rate limits, and HTTP headers at the boundary. FormRequest sanitizes and validates incoming payloads before the controller runs. Policy checks resource-level ownership and permissions. API Resource whitelists outgoing JSON fields so internal schema details never leak.

Should Laravel APIs return 404 or 403 for another user's resource?+

Return 404 by scoping queries through the authenticated user's relationship ($user->documents()->findOrFail($id)). Returning 403 leaks that the record ID exists (IDOR enumeration). Keep a Policy check as a secondary fallback.

Where do middleware and exception handlers live in Laravel 13 without Kernel.php?+

In bootstrap/app.php. Use ->withMiddleware() to append global middleware, prepend API middleware, or register aliases, and ->withExceptions() to render consistent JSON error envelopes.

Why pass Document::class instead of a model instance to FormRequest::authorize()?+

On a POST create endpoint, no model row exists yet. Passing the class string tells Laravel's Gate to resolve DocumentPolicy and call its create(User $user) method.

How do you avoid orphan files when a Laravel DB transaction fails?+

Store the uploaded file with a UUID filename, wrap the DB insert in DB::transaction() inside a try/catch, and delete the file inside the catch block if the transaction throws. On delete, commit the DB deletion first, then remove the file from disk.
