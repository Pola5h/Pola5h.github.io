Laravel Queue Workers in Docker: Why They Die & How to Fix It (2026)

By Kamruzzaman Polash · September 27, 2026 · 15 min read
Quick Answer

Laravel queue workers die in Docker due to 4 causes: memory leaks, uncaught exceptions, OOM kills, and no process manager.

The definitive fix: run workers with --max-time=3600 --max-jobs=500 --memory=256, and use Supervisor with autorestart=true and stopwaitsecs=3600. This makes workers exit gracefully before leaking memory, then restart automatically.

You deploy your Laravel app to Docker, push a queue job, and 30 minutes later — silence. The worker is gone. No logs. No errors. Just a dead container or a zombie process that's not picking up jobs.

This is one of the most common production problems Laravel developers face, and it's almost always preventable. This guide covers every reason workers die in Docker and the exact configuration to fix each one.

1. The 4 Reasons Laravel Queue Workers Die in Docker

Cause 1
Memory Leaks
PHP accumulates memory every job. Without a restart limit, memory grows until Docker's OOM killer terminates the process.
Cause 2
Uncaught Exceptions
Exceptions outside handle() — in middleware, serialization, or polling — crash the entire worker process, not just the job.
Cause 3
OOM Kill (SIGKILL)
Docker containers have memory limits. When the limit is hit, Linux sends SIGKILL — which cannot be caught or deferred. The worker dies mid-job.
Cause 4
No Process Manager
Without Supervisor or Horizon, a dead worker simply stays dead. No one restarts it. Jobs pile up silently.

Understanding which cause is killing your workers is important because the fix is different for each. Let's cover the solutions in order of importance.

2. --max-time and --max-jobs: The Core Fix for Memory Leaks

PHP is a long-running process when used as a queue worker. Each job it processes can leave behind small amounts of memory that are never garbage collected — Eloquent model caches, event listeners, static singletons. Over hours, this adds up.

The solution is not to fix every memory leak. The solution is to restart the worker periodically before it accumulates too much memory. Laravel provides two flags for this:

FlagWhat it doesRecommended value
--max-time=N Exit gracefully after N seconds (finishes current job first) 3600 (1 hour) Use in production
--max-jobs=N Exit after processing N jobs 500 Use in production
--memory=N Exit if memory exceeds N MB (checked between jobs) 256
--sleep=N Seconds to wait when queue is empty 3
--tries=N Max attempts before marking a job as failed 3
--timeout=N Seconds before a single job is killed 60
# ❌ WRONG — never run without limits in production php artisan queue:work # ✅ CORRECT — exits gracefully, Supervisor restarts automatically php artisan queue:work redis \ --queue=critical,default \ --max-jobs=500 \ --max-time=3600 \ --memory=256 \ --sleep=3 \ --tries=3 \ --timeout=60
Why use both --max-time AND --max-jobs? --max-jobs catches leaks on high-traffic queues (500 jobs processed, restart). --max-time catches leaks on low-traffic queues that process very few jobs over a long time (1 hour passed, restart). Together they cover all traffic patterns.
Important: --max-time was introduced in Laravel 8. If you're on Laravel 7 or earlier, you do not have this flag. Upgrade to use it.

3. Supervisor Configuration for Docker

Supervisor is the standard process manager for Laravel queue workers on Linux. It keeps workers running continuously — when a worker exits (from --max-time, --max-jobs, or a crash), Supervisor immediately starts a new one.

There are two ways to use Supervisor in Docker: run it as the container's main process, or run it alongside your app in a dedicated worker container. The dedicated container approach is strongly preferred in production.

Option A: Dedicated Worker Container (Recommended)

In docker-compose.yml, add a separate service that runs only the queue worker:

# docker-compose.yml services: app: build: . # Your main web service — serves HTTP requests queue-worker: build: . command: supervisord -c /etc/supervisor/conf.d/laravel-worker.conf -n restart: unless-stopped depends_on: - app environment: - QUEUE_CONNECTION=redis volumes: - ./storage:/var/www/html/storage

Supervisor Config File

Create this file at /etc/supervisor/conf.d/laravel-worker.conf inside your Docker image:

# /etc/supervisor/conf.d/laravel-worker.conf [unix_http_server] file=/var/run/supervisor.sock [supervisord] logfile=/var/www/html/storage/logs/supervisord.log pidfile=/var/run/supervisord.pid nodaemon=true [rpcinterface:supervisor] supervisor.rpcinterface_factory = supervisor.rpcinterface:make_main_rpcinterface [supervisorctl] serverurl=unix:///var/run/supervisor.sock [program:laravel-worker] process_name=%(program_name)s_%(process_num)02d command=php /var/www/html/artisan queue:work redis \ --sleep=3 \ --tries=3 \ --max-jobs=500 \ --max-time=3600 \ --memory=256 \ --timeout=60 \ --queue=critical,default autostart=true autorestart=true stopasgroup=true killasgroup=true user=www-data numprocs=2 redirect_stderr=true stdout_logfile=/var/www/html/storage/logs/worker.log stopwaitsecs=3600
Critical: stopwaitsecs MUST be equal to or greater than --max-time. If stopwaitsecs=60 but --max-time=3600, Supervisor will send SIGKILL to a worker that's been running for 61 seconds — terminating active jobs mid-execution. Always match them.
numprocs=2 runs 2 parallel workers. For a high-traffic queue, increase to 4–8. Monitor memory usage (docker stats) and adjust.

4. Dockerfile Setup (Complete Example)

Here's a production-ready Dockerfile that installs Supervisor and includes the worker config:

# Dockerfile FROM php:8.3-fpm-alpine # Install dependencies RUN apk add --no-cache supervisor redis # Install PHP extensions RUN docker-php-ext-install pdo pdo_mysql opcache RUN pecl install redis && docker-php-ext-enable redis WORKDIR /var/www/html # Copy app files COPY . . RUN composer install --no-dev --optimize-autoloader # Copy Supervisor config COPY docker/supervisor/laravel-worker.conf /etc/supervisor/conf.d/ # Set permissions RUN chown -R www-data:www-data storage bootstrap/cache RUN chmod -R 775 storage bootstrap/cache # Default: start Supervisor (for the worker container) CMD ["supervisord", "-n", "-c", "/etc/supervisor/conf.d/laravel-worker.conf"]
Tip: Use a multi-stage Dockerfile to keep the production image small. The worker container can share the same image as the web container — just override the CMD in docker-compose.yml to run supervisord instead of php-fpm.

5. Handling OOM Kills and Memory Limits

An OOM kill (Out of Memory kill) is different from a graceful exit. When Docker's memory limit is hit, the Linux OOM killer sends SIGKILL — which cannot be caught or handled by PHP. The worker dies immediately, mid-job.

How to prevent OOM kills:

# Set a container memory limit in docker-compose.yml services: queue-worker: mem_limit: 512m mem_reservation: 256m # Add --memory flag so PHP exits BEFORE the container hits its limit # If container limit = 512m and numprocs = 2: # Each worker should exit at 512m / 2 = 256m → --memory=200 (with headroom) php artisan queue:work --memory=200

The rule: --memory × numprocs should always be less than the container's mem_limit. Give 20–30% headroom for the base PHP process and Supervisor overhead.

Note: --memory is checked between jobs, not during a job. If a single job uses 400MB, the worker won't exit mid-job — it exits after the job finishes. Ensure your jobs themselves don't consume excessive memory.

6. Uncaught Exceptions and Worker Crashes

There are two types of exceptions in a Laravel queue worker:

  • Exception inside handle() — caught by Laravel, job is marked failed, worker continues.
  • Exception outside handle() — not caught, worker process crashes. This includes errors in: job serialization/deserialization, queue middleware, boot listeners, or Redis connection drops.
// ✅ Safe — exception inside handle() is caught by Laravel class ProcessOrder implements ShouldQueue { public function handle(): void { // If this throws, job fails but worker lives $this->processPayment(); } } // ❌ Dangerous — exception in constructor crashes the worker class BadJob implements ShouldQueue { public function __construct( public readonly Order $order // throws if Order is deleted ) {} }
# A Redis connection drop can crash the worker # Fix: set REDIS_RETRY_AFTER in .env to handle reconnects # Also: use phpredis extension with retry settings REDIS_HOST=redis REDIS_PORT=6379 REDIS_TIMEOUT=30 REDIS_RETRY_INTERVAL=500
Best practice: Even if you fix every exception source, Supervisor autorestart=true is still your safety net. If a worker crashes for any reason, Supervisor restarts it within 1 second. Design for resilience, not perfection.

7. Horizon vs queue:work in Docker

Laravel Horizon is the official Redis queue manager from the Laravel team. It replaces Supervisor-based queue:work management with a code-driven configuration and provides a real-time dashboard.

Featurequeue:work + SupervisorLaravel Horizon
Redis requiredNoYes (mandatory)
Dashboard UINoYes (real-time)
Auto-scaling workersNoYes
Metrics & throughputNoYes
Failed job UINo (artisan only)Yes
Docker complexitySimpleModerate
Worker restart handlingSupervisorAutomatic (built-in)

Running Horizon in Docker

# docker-compose.yml — Horizon replaces queue:work services: horizon: build: . command: php artisan horizon restart: unless-stopped depends_on: - redis environment: - QUEUE_CONNECTION=redis
# Handle graceful shutdown on SIGTERM (important in Docker) # Add to your entrypoint script: trap "php artisan horizon:terminate" SIGTERM SIGINT php artisan horizon wait
// config/horizon.php — configure worker pools 'environments' => [ 'production' => [ 'supervisor-1' => [ 'connection' => 'redis', 'queue' => ['critical', 'default'], 'balance' => 'auto', 'minProcesses' => 1, 'maxProcesses' => 10, 'tries' => 3, 'timeout' => 60, ], ], ],
Horizon handles memory management internally — you don't need --max-time or --max-jobs when using Horizon. It periodically restarts workers based on its own internal logic and the memory setting in config/horizon.php.

8. Production Checklist

Before deploying queue workers to production Docker, verify all of these:

# ✅ PRODUCTION QUEUE WORKER CHECKLIST # 1. queue:work command has --max-time, --max-jobs, --memory php artisan queue:work redis --max-jobs=500 --max-time=3600 --memory=256 # 2. Supervisor stopwaitsecs >= --max-time value stopwaitsecs=3600 # in supervisord.conf # 3. Container mem_limit > (--memory × numprocs) with headroom mem_limit: 512m # for 2 workers × 200MB each # 4. Failed jobs table exists php artisan queue:failed-table php artisan migrate # 5. Workers restart after deployment php artisan queue:restart # or: php artisan horizon:terminate # 6. QUEUE_CONNECTION set correctly in .env QUEUE_CONNECTION=redis # 7. Supervisor autorestart=true autorestart=true # in supervisord.conf # 8. Log files are writable chmod -R 775 storage/logs

Always restart workers after deployment

# Add to your deployment script (CI/CD pipeline) php artisan queue:restart # graceful restart for queue:work + Supervisor php artisan horizon:terminate # graceful restart for Horizon # queue:restart signals workers to stop after their current job # Supervisor restarts them with the new code automatically
Don't skip queue:restart after deployment. Workers cache your application code in memory. If you deploy new code without restarting workers, they continue running old code. This causes subtle bugs that are extremely hard to debug.

Conclusion

Laravel queue workers die in Docker for predictable, fixable reasons. The core solution is always the same: use --max-time and --max-jobs to restart workers before they leak memory, and use Supervisor (or Horizon) with autorestart=true to keep them running continuously.

The full checklist above covers every cause. Apply it to your production setup and your workers will run stably — even on a busy queue with millions of jobs per day.
